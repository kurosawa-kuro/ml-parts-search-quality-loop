# オンライン精度を、この土台で学ぶ

読み手は、モデル・前処理・訓練・評価・オフラインとオンライン・パイプラインを一通り知っていて、表計算型のコンペで特徴と検証の切り方を経験している人である。検索ランキングを職業にしてはいない。

本職は AI プラットフォーム / MLOps で、参画先は EC の検索である。VectorSearch、Elasticsearch、LightGBM のリランキングは DS が組み、その改善をプラットフォーム側で受けている。スクリプトジョブの並列化、推論 API のバッチ化、Feature Store、散らばった評価プログラムの統合が日常の仕事である。

このフォルダは、その立場の人が **オフラインは良くなったのにオンラインが動かないとき、どのジョブを回し直すか** を、このリポジトリで検証するための読み順である。LightGBM の目的関数を導出する資料ではない。

## 参画先との対応

このリポジトリは部品の架空カタログで、検索経路はベクトルだけである。Elasticsearch のキーワード側は入っていない。ハイブリッドを足す話には使わない。

| 参画先で触っているもの | このリポジトリでの対応 | 学習上の使い方 |
|---|---|---|
| VectorSearch への投入と、商品キーワードからのベクトル取得 | Qdrant への固定 revision の E5。retrieval はバッチ | 候補 100 件が後段の入力表になる。ここを変えた実験と、表を固定した実験を混ぜない |
| LightGBM リランキング | 同じ候補表の上の LambdaRank。列は `parts_features_v1` | オフラインの NDCG が動いても、1 位の KPI が動くとは限らない。動いた列を Feature Store の版として固定する |
| 散らばった評価スクリプト | 一つの MetricPolicy と、一つの SimulationPolicy と、一つの `decision` | NDCG を出すノートと、成功率を出すノートが別々に緑でも、採用は一つの関門で決める |
| Feature Store | `feature_schema.json` の列順と checksum。学習時と推論時が一致しないと止める | バッチ推論で足した列が、学習ジョブの列とずれていないかを、点数の前に見る |
| ジョブの切り直し | stage ごとの不変 run。評価は検索を再実行しない | オンラインだけ悪いとき、VectorSearch のジョブと LightGBM のジョブのどちらを回すかを、失敗種別で決める |

## このフォルダの位置

01〜08 は挙動の契約である。コードと設定がそれより上である。
[元設計メモ](../archive/search-quality-loop-brainstorm.md) は、なぜこのリポジトリを作ったかの出所である。

このフォルダは契約でも作業タスクでもない。
挙動が食い違ったらコードと 01〜08 に従う。目的が食い違ったら元メモに戻る。
`exit 0` は、オンライン精度の判断ができるようになったことではない。
