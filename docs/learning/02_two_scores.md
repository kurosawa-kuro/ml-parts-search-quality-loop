# 二つの点数

オフラインとオンラインは、同じ検索結果について別の質問をしている。
片方が上がればもう片方も上がる、とは限らない。そのずれを見るために二つある。

## オフラインが聞いていること

「正解の部品は、リストのどのあたりにいるか。」

クエリごとに、カタログ全体へルールで点数を付けた正解データがある。relevance は 0〜4 で、4 が型番の完全一致、0 が別カテゴリや必須条件違反である。

| 指標 | 平たい意味 | リストのどこを見るか |
|---|---|---|
| Recall@100 | 適合する部品のうち、候補の上位 100 件に入った割合 | 100 件まで。順位の良し悪しは見ない |
| MRR@100 | 最初の適合が何位にいたかの逆数 | 最初の 1 件の順位 |
| NDCG@10 | 適合度の高いものほど上にいるか。10 位まで | 並び全体。2 位や 8 位の改善も点数になる |

集計はクエリ単位の平均である。返ってこなかったクエリを「0 件の成功」と混ぜない。失敗は null のまま残し、平均から消さない。

このリポジトリでは、オフラインの主指標は NDCG@10 である。Recall と MRR は、それを良くするついでに壊していないかのガードレールである。

## オンラインが聞いていること

「最初に見せた 1 件は、探すのをやめられるものか。」

疑似ユーザーは順位が下がるほど見なくなる。規則は `1 / 順位` で、1 位は必ず候補になり、10 位はほとんど見られない。
だからオンラインの点数は、10 件の並びの美しさではなく、**1 位**でほぼ決まる。

採否に使うのは次の二つである。定義は [simulation.py](../../src/parts_search/pipelines/simulation.py) と [05](../05_data_model.md) に従う。

| 指標 | 平たい意味 |
|---|---|
| 検索成功率 `searchSuccessRate` | 観測が閉じた提示のうち、最上位の relevance が 2 以上である割合 |
| 誤適合率 `wrongFitmentRate` | 中身がある提示のうち、最上位の relevance が 0（必須条件違反）である割合 |

一緒に記録するが、採否の合否そのものではないもの:

| 指標 | 平たい意味 |
|---|---|
| CTR | 1 回以上クリックされた提示の割合 |
| 再検索率 | 観測窓の中で検索をやり直した提示の割合 |
| 0 件率 | 返す商品が空だった提示の割合 |
| 購入率 | 観測窓の中で購入まで進んだ提示の割合 |

クリックや購入は、適合度と位置バイアスから作った架空の行動である。
実ユーザーの嗜好を測った値ではない。

## なぜ食い違うか

NDCG@10 は、正解が 20 位から 4 位へ上がっただけでも良くなる。
検索成功率は、その部品が 1 位になるまで動かない。

ベクトル類似は「M6 の SUS ボルト」と「M8 の SUS ボルト」を近くに置く。
意味は近い。部品としては寸法が違うので relevance は 0 である。
1 位が M8 のまま 4 位の M6 が 2 位に上がると、NDCG は上がり、誤適合率は下がらない。

逆に、候補 100 件に正解が入っていないときは、順位学習をどれだけ回しても 1 位を正解にできない。
このときは Recall@100 が悪く、検索成功率も悪いままである。直す場所は順位ではなく検索である。

## 三つに分ける理由

学習に使ったクエリで点数が上がるのは当然に近い。
このリポジトリは family（同じ意図のクエリの束。日英はその束の中に入る）を単位に分けている。

| 分割 | 使い道 |
|---|---|
| train | 順位モデルをフィットする |
| tuning | 設定を選ぶ。学習のフィットには使わない |
| holdout | オフラインの独立比較。開発中に見続けて閾値を動かさない |
| production | 疑似オンライン。採否の直前まで改善材料にしない |

同じ family が二つに入ると、翻訳や言い換えで答えが漏れる。
オンラインの失敗を見て正解データを書き換え、その同じクエリで再評価して合格、は測定にならない。
クリックは正解の候補として残り、評価用の正解へは自動では昇格しない。
